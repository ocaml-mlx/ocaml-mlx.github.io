How it works

Follow a .mlx expression from the parser to an ordinary OCaml program, then connect the same path to Dune and editor tools.

The compilation path

A .mlx file starts as OCaml with JSX-shaped expressions. mlx-pp parses it into an OCaml syntax tree, then the installed OCaml compiler checks and compiles that tree. Your component functions or a later PPX define what the resulting calls do. mlx does not provide an HTML renderer or replace ocamlc.

A modified OCaml parser

The mlx source includes adapted OCaml lexer and parser code. Its lexer recognizes opening and closing tags; its parser accepts elements as expressions alongside ordinary OCaml expressions. This is a fork of the parsing layer, not a fork you must use as your application compiler. The mlx package installs the mlx-pp preprocessor.

By default, mlx-pp writes a binary OCaml syntax tree for the compiler, not a text .ml file. To inspect readable OCaml, use its real -print-ml option:

The parser produces a tree for its vendored OCaml version. mlx-pp uses ppxlib to migrate that tree to the compiler AST version it was built with, then writes the compiler's binary AST header and tree. This is why the modified parser can work with a supported, ordinary OCaml compiler. The parser and your application's compiler do not have to be the same fork.

Inspect the generated OCaml · shell
mlx-pp -print-ml example.mlx

Elements become calls

Consider this complete program. Its helpers use plain strings so you can run it without a UI framework or PPX:

example.mlx
let tag ~class_ ~children () =
  "<" ^ class_ ^ ">" ^ String.concat "" children ^ "</" ^ class_ ^ ">"

let text ~children () = String.concat "" children

module Badge = struct
  let createElement ~label ~children () =
    "[" ^ label ^ ":" ^ String.concat "" children ^ "]"
end

let () =
  print_endline
    <tag class_="demo"><text>"Hello"</text><Badge label="mlx">"!"</Badge></tag>

The lowercase <tag> and <text> call functions in scope. The capitalized <Badge> calls Badge.createElement. Attributes become labeled arguments such as ~class_:"demo" and ~label:"mlx". Nested expressions become one ~children list. Every element call also receives an unlabeled () argument first. The relevant part of mlx-pp -print-ml example.mlx looks like this; only the helper declarations and whitespace are omitted:

Generated OCaml · excerpt
print_endline
  ((tag ()
      ~children:[((text () ~children:["Hello"]) [@JSX ]);
                 ((Badge.createElement () ~children:["!"] ~label:"mlx")
                  [@JSX ])]
      ~class_:"demo")
   [@JSX ])

Why the JSX attribute remains

The [@JSX] attribute marks each generated element application. It lets a downstream PPX recognize JSX calls instead of guessing from ordinary function calls. A fragment has no tag to call: its list of children, or its spread expression, carries the marker instead. A PPX may use these markers to implement a framework's behavior, but a PPX is not required. In the program above, the OCaml compiler accepts the marked calls and the plain functions build the result.

Compile directly with ocamlc

Install mlx and make sure mlx-pp and ocamlc are on your PATH. Save the program above as example.mlx, then run:

Compile and run · shell
ocamlc -pp mlx-pp -impl example.mlx -o example
./example

The -pp option runs mlx-pp before parsing by the compiler; -impl identifies example.mlx as an implementation. The program prints:

Output
<demo>Hello[mlx:!]</demo>

Build the same program with Dune

For a new project, save the following dune-project beside example.mlx. You need Dune 3.16 or newer for this dialect. A build needs only the mlx preprocessor, OCaml, and Dune.

dune-project · minimal
(lang dune 3.16)
(name mlx_toolchain_example)

(dialect
 (name mlx)
 (implementation
  (extension mlx)
  (preprocess
   (run mlx-pp %{input-file}))))

(name mlx) registers the dialect. (extension mlx) selects .mlx implementation files. (preprocess (run mlx-pp %{input-file})) gives Dune the source file and writes the binary syntax tree to stdout for the compiler. The dialect does not change .mli files here.

Save this in a file named dune in the same directory:

dune
(executable
 (name example))
Build and run · shell
dune exec ./example.exe

It prints the same output shown above. If your application uses a downstream PPX, configure it in the usual Dune library or executable stanza after this syntax preprocessing step. The mlx dialect does not choose that PPX.

Add editor and formatter support when needed

The following version adds two independent tools. Install ocamlmerlin-mlx and ocamlformat-mlx before you copy these optional fields:

dune-project · editor and formatter
(lang dune 3.16)
(name mlx_toolchain_example)

(dialect
 (name mlx)
 (implementation
  (extension mlx)
  (merlin_reader mlx)
  (format
   (run ocamlformat-mlx %{input-file}))
  (preprocess
   (run mlx-pp %{input-file}))))

(merlin_reader mlx) selects the ocamlmerlin-mlx reader extension for Merlin's editor parsing. Its adapted Merlin parser reports source errors and converts the result for Merlin. It is not a replacement OCaml compiler or a full replacement for Merlin or OCaml LSP. (format (run ocamlformat-mlx %{input-file})) runs the separate OCamlFormat fork when formatting a .mlx source file; it is not part of compilation. Leave either clause out if you do not use that tool. The preprocess clause is the one the compiler build needs.

Where a downstream PPX fits

The order is .mlx source → mlx parsing → marked OCaml calls → optional downstream PPX → normal type checking and compilation. Do not substitute ocamlc -ppx mlx-pp for -pp mlx-pp. A PPX runs after the compiler parses its input, so it cannot teach the ordinary compiler parser to read JSX tags. Use the libraries guide to choose the functions or PPX that give your tags their behavior.

Sources and version scope

This explanation follows mlx source at revision e458060, just after release 0.12. That release added fragment and children-spread syntax; the later revision also rejects an explicit children prop combined with nested children. The standalone program and Dune example were run with OCaml 5.5.0 and Dune 3.24.2. They do not test the companion editor or formatter binaries.
